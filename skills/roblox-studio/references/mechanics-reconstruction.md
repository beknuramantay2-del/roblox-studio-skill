# Воссоздание игровых механик по ТЗ или референсу

Не копируй игру целиком и не начинай с красивого UI. Сначала выдели наблюдаемое поведение и собери минимальный вертикальный срез.

## Декомпозиция механики

Опиши механику пятью слоями:

1. **Intent:** что игрок пытается сделать и почему это приятно.
2. **Loop:** input → validation → state change → feedback → reward/progression.
3. **Entities:** Player, item, target, zone, round, currency и их состояния.
4. **Authority:** что решает сервер, что предсказывает клиент, что только визуализируется.
5. **Failure:** spam, смерть, respawn, leave, reconnect, invalid input, missing asset.

Пример боевой атаки:

```text
Input: Activated / key / touch
Client: animation + anticipation FX
Server: cooldown + distance + target validation
State: damage applied once
Feedback: hitstop, sound, number, knockback
Persistence: reward/XP only after server result
```

## Вертикальный срез

Собери сначала один полностью рабочий путь: один игрок, одна цель, одна награда, один экран, один тест. Затем расширяй количество предметов, врагов и вариантов. Большой незапущенный каркас хуже маленькой доказанной механики.

## Референсы без слепого копирования

Из референса извлекай правила: темп, дистанция, окно реакции, визуальный язык, порядок действий. Не копируй чужие ассеты, названия, тексты или защищённые элементы. Оригинальная реализация должна быть самостоятельной.

## Acceptance table

До кода заполни:

| Сценарий | Ожидание | Проверка |
| --- | --- | --- |
| happy path | действие даёт результат один раз | Playtest |
| repeat | второе действие уважает cooldown/idempotency | повтор |
| invalid | сервер ничего не меняет | подделанный remote |
| respawn | состояние восстанавливается | смерть/респавн |
| leave | нет ошибок и утечек | выход во время yield |
| multiplayer | игроки видят одно состояние | 2 клиента |

Так средняя модель не заменяет проектирование случайным кодом и понимает, когда механика действительно готова.
