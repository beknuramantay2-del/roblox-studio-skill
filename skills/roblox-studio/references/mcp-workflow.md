# Работа через Studio MCP

Ты подключён к **живой** сессии Studio. Это не файлы на диске: изменения применяются к открытому проекту сразу, а Ctrl+Z у пользователя не всегда откатывает то, что сделал агент скриптом. Отсюда весь стиль работы ниже.

## Сначала смотри, потом пиши

Прочитай дерево нужной ветки (`ServerScriptService`, `ReplicatedStorage`, `StarterGui`, `Workspace`) прежде чем создавать что-либо. Ты ищешь ответ на один вопрос: **это уже существует?**

Если существует — правь. Создание второго `ShopHandler` рядом с первым не ломает Studio сразу, зато потом даёт баг, который выглядит как "кнопка срабатывает дважды" и отлаживается часами. Прежде чем добавить скрипт, проверь, нет ли уже такого имени в родителе.

Перед крупной правкой в существующей системе прочитай файл целиком, а не первые 20 строк. Luau-модули часто держат состояние в замыканиях сверху файла, и правка в середине без этого контекста ломает инварианты.

## Изменения делай мелкими и обратимыми

Одна задача = одна связная правка = одна проверка. Не создавай пятнадцать инстансов и три скрипта одним залпом: если что-то сломается, ты не поймёшь, что именно, а разбирать придётся вручную в чужом дереве.

Когда генерируешь инстансы кодом, пиши код **идемпотентно**: сначала проверь, есть ли объект, и переиспользуй его.

```lua
local function ensure(parent: Instance, className: string, name: string): Instance
	local existing = parent:FindFirstChild(name)
	if existing and existing.ClassName == className then
		return existing
	end
	if existing then
		existing:Destroy() -- имя занято объектом другого типа
	end
	local new = Instance.new(className)
	new.Name = name
	new.Parent = parent
	return new
end
```

Повторный запуск такого кода не плодит дубликаты. Это критично, потому что ты будешь запускать свой генератор UI по пять раз, доводя внешний вид.

## Разрушительные действия требуют слова пользователя

Сам, без спроса, не делай: `:Destroy()` на том, что создал не ты; удаление или переименование существующих скриптов; массовые правки Workspace; изменение Game Settings; чистку DataStore. Спроси одной фразой и предложи вариант: "Там уже есть OldShopGui, снести или переименовать в бэкап?"

Если надо заменить что-то существующее, безопаснее переименовать старое в `Name_old` и оставить, чем удалить. Пользователь сам почистит, когда убедится, что новое работает.

## Запуск кода в Studio

Запуск Luau в сессии — твой основной способ проверки. Пользуйся им, но помни:

- **Edit-режим не равен Run-режиму.** В Edit нет игрока, `Players.LocalPlayer` пустой, `PlayerAdded` не сработает. Проверять геймплей надо в плейтесте, а UI и генерацию окружения можно и в Edit.
- **Пиши в скрипт, а не только выполняй.** Код, выполненный разово в сессии, исчезнет. Если это часть игры, он должен лежать в реальном `Script`/`ModuleScript`. Разово запускай только генераторы (построить UI, расставить part-ы) и диагностику.
- **Диагностику начинай с чтения Output.** Прежде чем чинить по догадке, посмотри фактическую ошибку и стек. Догадки про Roblox-баги ошибаются чаще, чем кажется: симптом "кнопка не нажимается" одинаково выглядит при нулевой прозрачности, при `Active = false`, при перекрывающем фрейме и при отсутствующем соединении.
- **Логируй с префиксом системы**: `print("[Shop] куплено:", itemId)`. В Output Roblox мешает всё вместе, безымянные print-ы бесполезны.

## Плейтест

Перед переключением режима убедись, в каком ты сейчас: агенты стабильно застревают, пытаясь войти в Play из Play. Проверь состояние, потом переключай.

После остановки плейтеста **все изменения, сделанные в Run-режиме, теряются**. Никогда не правь скрипты и не строй UI во время плейтеста, ожидая, что это сохранится. Останови, потом правь.

## Что сказать пользователю

Он видит своё дерево в Explorer, поэтому называй точные пути: `ReplicatedStorage/Modules/Shop`, а не "я добавил модуль магазина". Если для проверки нужен Play — скажи, что нажать и на что смотреть. Один-два пункта, не инструкция на страницу.
