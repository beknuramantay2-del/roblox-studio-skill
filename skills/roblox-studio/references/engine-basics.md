# Устройство Studio и движка

База, без которой всё остальное ломается. Большинство необъяснимых багов новичка — это код, положенный не в тот контейнер.

## Explorer: где что живёт и почему

| Контейнер | Что кладём | Кто видит |
| --- | --- | --- |
| `Workspace` | всё физическое: карта, модели, персонажи | все, реплицируется |
| `ServerScriptService` | серверная логика (`Script`, `ModuleScript`) | только сервер |
| `ServerStorage` | шаблоны и данные для сервера | только сервер |
| `ReplicatedStorage` | общий код, remote-ы, шаблоны для клиента | сервер и клиент |
| `ReplicatedFirst` | то, что должно загрузиться до всего (loading screen) | клиент, первым |
| `StarterPlayer/StarterPlayerScripts` | клиентская логика (`LocalScript`) | клиент |
| `StarterPlayer/StarterCharacterScripts` | скрипты, копируемые в персонажа при каждом респавне | клиент |
| `StarterGui` | `ScreenGui`, копируется в `PlayerGui` при спавне | клиент |
| `StarterPack` | инструменты (`Tool`), выдаваемые всем при спавне | клиент |
| `Players` | объекты игроков, `leaderstats` живут здесь | все |
| `Lighting` | освещение, `Atmosphere`, `Sky` | клиент рендерит |
| `SoundService` | глобальные звуки и группы громкости | клиент |
| `Teams` | команды | все |

Ключевое понимание: `StarterGui` и `StarterPack` — это **шаблоны**, а не то, с чем работает игрок. Roblox копирует их содержимое в `player.PlayerGui` и `player.Backpack` при каждом спавне. Поэтому правка `StarterGui` в рантайме не влияет на уже вошедшего игрока, а изменения в `PlayerGui` теряются при респавне, если у `ScreenGui` стоит `ResetOnSpawn = true`. Ставь `ResetOnSpawn = false` на всё, чьё состояние должно переживать смерть — иначе открытый инвентарь будет закрываться при каждом респавне.

Всё, что лежит в `ServerStorage` и `ServerScriptService`, клиенту физически недоступно. Это единственный надёжный способ спрятать данные. Прятать в `ReplicatedStorage` бессмысленно: клиент читает его целиком.

## Properties: что важно знать

Свойства читаются и пишутся из кода так же, как в панели. Полезные привычки:

- Изменение свойства объекта в `Workspace` реплицируется всем клиентам. Массовые правки в цикле по тысяче частей завалят сеть, см. `performance.md`.
- `Name` — не идентификатор. Дубликаты имён легальны, `FindFirstChild` вернёт первый попавшийся. Для идентификации используй теги и атрибуты (`building-models.md`).
- Свойства, которых нет в панели Properties, но есть в API, тоже доступны из кода: панель показывает не всё.
- `GetPropertyChangedSignal("Свойство")` дешевле и точнее, чем `Changed` на всём объекте.
- Изменения, сделанные скриптом во время плейтеста, **не сохраняются**. Правь только в Edit-режиме.

## Part, Model, Folder, Attachment

**`Part`** — базовый физический объект. Ключевые свойства: `Size`, `CFrame` / `Position`, `Anchored`, `CanCollide`, `CanTouch`, `Material`, `Color`, `Transparency`, `Massless`, `CollisionGroup`.

**`Model`** — контейнер для физических объектов. Обязателен `PrimaryPart`, иначе `PivotTo`, `MoveTo` и `GetPivot` ведут себя непредсказуемо. Двигай модель целиком через `model:PivotTo(cframe)`, а не по частям: иначе она разъедется.

**`Folder`** — чистая группировка без физики и трансформа. Для организации скриптов и логических групп используй именно `Folder`, а не `Model`: `Model` тянет за собой трансформ и участвует в лишних расчётах.

**`Attachment`** — точка привязки внутри части. Нужна для констрейнтов (`RopeConstraint`, `AlignPosition`, `Motor6D`), эффектов (`ParticleEmitter`, `Beam` и `Trail` цепляются к двум Attachment) и оружия. Позиция задаётся в локальных координатах родителя, поэтому Attachment едет вместе с частью автоматически — в этом весь смысл.

```lua
local attachment = Instance.new("Attachment")
attachment.Name = "MuzzlePoint"
attachment.Position = Vector3.new(0, 0, -1.5) -- локально относительно части
attachment.Parent = weaponPart
```

Соединяй части через `WeldConstraint` (жёстко, современный способ), не через устаревший `Weld` с ручными `C0` и `C1`. Для сложных сборок делай одну часть `Anchored`, остальные приваривай к ней.

## Script, LocalScript, ModuleScript

| Тип | Где работает | Откуда запускается |
| --- | --- | --- |
| `Script` | сервер | `ServerScriptService`, `Workspace`, внутри `Tool` |
| `LocalScript` | клиент | `StarterPlayerScripts`, `StarterCharacterScripts`, `PlayerGui`, `Backpack` |
| `ModuleScript` | там, откуда его требуют | где угодно, сам не запускается |

`LocalScript` в `Workspace` **не запустится**. Это самая частая ошибка новичка: код выглядит правильным, ошибок нет, ничего не происходит. Он работает только внутри персонажа игрока, `PlayerGui`, `Backpack` и `StarterPlayerScripts`.

У современного `Script` есть свойство `RunContext`, позволяющее ему работать как клиентский. Не смешивай подходы в одном проекте: путаница дороже удобства. Держись простого правила `Script` = сервер, `LocalScript` = клиент.

`ModuleScript` возвращает одно значение (обычно таблицу) и **кэшируется**: повторный `require` из того же контекста отдаёт тот же объект, код не выполняется заново. Это делает модуль удобным синглтоном для состояния сервиса. Но помни: сервер и клиент требуют модуль независимо, у каждого свой экземпляр. Общее состояние через модуль между сторонами не работает, только через remote.

## Client и Server: главное разделение

Сервер один, клиентов много, и каждый клиент полностью под контролем игрока. Отсюда:

- Сервер видит всё и владеет истиной: валюта, инвентарь, здоровье, прогресс.
- Клиент видит только реплицированное и отвечает за ощущения: ввод, камера, звук, UI, предсказание.
- Клиент не может напрямую вызвать серверную функцию, только через `RemoteEvent` или `RemoteFunction`.
- Изменения, сделанные клиентом в `Workspace`, **другим игрокам не видны** и живут только у него. Это коварная ловушка: у себя на экране всё работает, у остальных не произошло ничего.

### RemoteEvent

Односторонняя посылка сообщения, ничего не возвращает и не ждёт. Основной инструмент, покрывает почти все задачи.

```lua
-- клиент просит
Remotes.RequestPurchase:FireServer(itemId)

-- сервер отвечает конкретному игроку
Remotes.PurchaseResult:FireClient(player, true)

-- сервер сообщает всем
Remotes.RoundStarted:FireAllClients(roundDuration)
```

Первый аргумент в `OnServerEvent` — это `player`, его подставляет Roblox, подделать нельзя. Никогда не принимай игрока как аргумент от клиента: это дыра, позволяющая действовать от чужого имени.

### RemoteFunction

Вызов с ожиданием ответа. Клиент к серверу (`InvokeServer`) допустим, когда ответ нужен немедленно и логика простая.

**Сервер к клиенту (`InvokeClient`) не используй никогда.** Клиент может не ответить (одна строчка у читера), и серверный поток повиснет навсегда. Нужны данные от клиента — `RemoteEvent` в обе стороны с таймаутом.

В целом предпочитай `RemoteEvent`: он не блокирует и не создаёт классов ошибок, связанных с ожиданием. `RemoteFunction` оправдан для запросов вида "дай текущее состояние магазина" при открытии UI.

### Создание remote-ов

Создавай заранее в `ReplicatedStorage/Remotes`, **никогда не в рантайме**: клиент может подписаться до появления объекта и молча ничего не получать. Имена по смыслу и стороне: `RequestPurchase` (клиент просит), `BalanceUpdated` (сервер сообщает). Из имени должно быть видно, кто кому и зачем — это резко снижает шанс написать логику начисления на клиенте.

Валидация всех аргументов на сервере обязательна, см. `security.md`.
