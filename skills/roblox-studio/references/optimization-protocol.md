# Протокол оптимизации и неопределённости

## Confidence

Для каждого важного решения помечай confidence: `high` если подтверждено проектом/официальной документацией/тестом, `medium` если следует из локального паттерна, `low` если это предположение. Low-confidence решение нельзя применять разрушительно: сначала probe или вопрос.

## Contradiction check

Перед изменением проверь четыре конфликта:

- существующий проектный convention против skill default;
- client/server ownership против удобства реализации;
- Edit DataModel против runtime DataModel;
- новый контракт против старых consumers.

При конфликте сначала сохраняй рабочий контракт проекта, затем предлагай миграцию. Не смешивай два источника истины.

## Cost control

Оцени изменение как `small`, `medium` или `large`. Small можно делать микрошагом; medium требует acceptance table; large требует checkpoint, vertical slice и подтверждения состояния после каждого слоя. Не создавай десятки файлов для проверки одной идеи.

## Evidence quality

Сильное evidence: runtime result, Output excerpt, Script Analysis result, screenshot, metric или воспроизводимый test command. Слабое evidence: код выглядит логично, Instance создан, ошибок пока не видно.

## User intent

Если запрос двусмыслен, выбери безопасную интерпретацию для маленького vertical slice и сообщи её одной строкой. Задавай вопрос только когда неправильная трактовка может удалить данные, потратить Robux, сломать production или изменить публичный контракт.
