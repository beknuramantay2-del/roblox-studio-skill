# Здоровье, урон, оружие, бой

## Здоровье и урон живут на сервере

Клиент может показывать полоску здоровья и эффект попадания, но считать урон обязан сервер. Клиентский расчёт урона означает бессмертие и мгновенные убийства у любого читера.

```lua
-- Единая точка нанесения урона. Все механики идут через неё,
-- иначе броня, иммунитет и статистика будут работать выборочно.
function CombatService.applyDamage(
	target: Humanoid,
	amount: number,
	source: Player?
): boolean
	if target.Health <= 0 then return false end          -- уже мёртв
	if not RemoteGuard.isNumber(amount, 0, MAX_DAMAGE) then return false end
	if source and isFriendly(source, target) then return false end

	local final = amount * getDefenseMultiplier(target)
	target:TakeDamage(final)  -- уважает ForceField, в отличие от Health -= x

	if source then
		Remotes.HitConfirmed:FireClient(source, target.Parent.Name, final)
	end
	if target.Health <= 0 then
		CombatService.onKill(source, target)
	end
	return true
end
```

Детали, которые дают баги:

- **`TakeDamage` вместо `Health -= x`.** Первый уважает `ForceField` (защиту на спавне), второй нет. Игрок, умирающий на спавне, — это почти всегда прямая запись `Health`.
- **Проверка `Health <= 0` в начале.** Без неё труп получает урон повторно, и `Died` может отработать дважды, начислив два убийства.
- **Максимальный урон.** Ограничение сверху защищает от бага с умножением и от подделанного значения.
- **Одна точка входа.** Как только урон наносится в трёх местах напрямую, любое изменение правил (щиты, иммунитет после респавна) придётся вносить трижды, и одно место забудут.

При смерти обязательно: снять статусы, очистить таблицы по игроку, отменить активные кулдауны. Забытая запись в таблице по мёртвому персонажу — утечка и источник ошибок при респавне.

## Оружие

Стандартный контейнер — `Tool` в `Backpack` (или `StarterPack` для выдачи всем). Внутри: `Handle` с `Attachment` для эффектов, `LocalScript` для ввода и ощущений, серверная логика в сервисе.

Распределение:

- **Клиент:** нажатие, анимация замаха, звук, эффект, локальное предсказание попадания.
- **Сервер:** проверка кулдауна, проверка дистанции и правдоподобности, расчёт и нанесение урона.

```lua
-- клиент, внутри Tool
tool.Activated:Connect(function()
	if os.clock() - lastSwing < COOLDOWN then return end  -- только для UX
	lastSwing = os.clock()
	playSwingAnimation()
	Remotes.Swing:FireServer()  -- без данных о цели: сервер решит сам
end)
```

Обрати внимание: клиент **не сообщает, в кого попал**. Для ближнего боя сервер сам ищет цели в зоне. Это исключает целый класс читов "убить любого с любого расстояния".

## Ближний бой

Сервер проверяет зону перед игроком в момент удара. Не через `Touched` на невидимой части (даёт двойные срабатывания и промахи на лагах), а через явный поиск.

```lua
local HIT_RANGE = 8
local HIT_ANGLE = 0.5  -- dot > 0.5 это примерно 60 градусов спереди

Remotes.Swing.OnServerEvent:Connect(function(player)
	if not RemoteGuard.check(player, "Swing", COOLDOWN) then return end
	local root = getRoot(player)
	if not root then return end

	local alreadyHit = {}  -- один удар = один урон на цель
	for _, other in Players:GetPlayers() do
		if other == player then continue end
		local otherRoot = getRoot(other)
		if not otherRoot then continue end

		local delta = otherRoot.Position - root.Position
		if delta.Magnitude > HIT_RANGE then continue end
		if root.CFrame.LookVector:Dot(delta.Unit) < HIT_ANGLE then continue end
		if alreadyHit[other] then continue end

		alreadyHit[other] = true
		CombatService.applyDamage(getHumanoid(other), WEAPON_DAMAGE, player)
	end
end)
```

Таблица `alreadyHit` не формальность: без неё цель, состоящая из нескольких частей, получает урон за каждую.

Для детской игры делай зону попадания **щедрой**. Если ребёнок визуально попал, а игра сказала "промах", он решит, что игра сломана. Лучше немного нечестно в пользу игрока, чем строго и фрустрирующе.

## Дальний бой

Два подхода, выбирай по механике:

**Мгновенный (hitscan).** Сервер делает raycast из позиции игрока в направлении взгляда, см. `physics-and-raycast.md`. Клиент рисует трассер и вспышку локально, не дожидаясь ответа: так стрельба ощущается мгновенной, хотя урон считает сервер.

**Снаряд (projectile).** Визуальный снаряд летит на клиенте у всех, а сервер считает попадание либо по своему такому же расчёту, либо по проверке заявки клиента с валидацией времени и траектории. Не делай физическую пулю на сервере с `Touched`: это дорого, лагает и промахивается.

В обоих случаях сервер обязан проверить кулдаун и то, что заявленное направление физически возможно из позиции игрока.

## Кулдауны

Два уровня, и это не дублирование:

- **На клиенте** — чтобы UI не давал спамить и кнопка визуально перезаряжалась. Защиты ноль.
- **На сервере** — единственная реальная защита. Через `RemoteGuard.check`.

Показывай кулдаун визуально: круговая заливка на кнопке или затемнение с числом. Ребёнок должен видеть, почему кнопка не работает, иначе решит, что игра зависла.

## Хитбоксы и ощущение боя

Что делает бой приятным (и это в детских играх важнее баланса):

- Мгновенная обратная связь: звук, вспышка, всплывающее число урона в первый же кадр, до подтверждения сервера.
- Небольшая пауза в анимации на моменте попадания (hit stop) — придаёт весомость.
- Слабый knockback, яркий эффект. Не отбирай у ребёнка контроль надолго.
- Полоска здоровья над целью крупная и цветная, с плавным уменьшением.
- Смерть не наказывает: быстрый респавн, ничего не теряется. Потеря прогресса за смерть в детской игре убивает удержание.

## Teams и дружественный огонь

`Teams` плюс `player.Team` — встроенный способ различать своих. Проверяй `isFriendly` в единой точке урона, а не в каждой механике.

В детских PvP-играх дружественный огонь почти всегда стоит выключить: он провоцирует конфликты и жалобы. Если он нужен по дизайну, сделай его явно видимым (другой цвет числа урона), чтобы не казалось багом.
