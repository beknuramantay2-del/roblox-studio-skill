# Контракты проекта

Средняя модель часто пишет код, который работает только внутри одного файла. Контракт связывает сервер, remote и клиент до реализации.

## Карточка системы

Перед кодом зафиксируй:

- цель и пользовательский сценарий;
- владелец состояния: серверный сервис;
- структура данных и миграция;
- публичные методы сервиса;
- remote-контракт: имя, направление, аргументы, типы, ответы, cooldown;
- клиентский controller и UI-состояния;
- очистка connections/instances;
- acceptance criteria и edge cases.

Пример:

```text
ShopService
State: DataService.Inventory, DataService.Coins
RequestPurchase(itemId: string) -> PurchaseResult
PurchaseResult: ok: boolean, reason: PurchaseReason?, balance: number
Rules: whitelist itemId, server price, atomic debit+grant, save after success
Tests: success, not enough, invalid id, spam, full inventory, player leaves
```

## Схема данных раньше кода

Описывай дефолт, обязательные поля, допустимые диапазоны, версию и миграцию. Не храни вычисляемые значения, если их можно получить из источника истины. Проверяй загруженные данные как недоверенный ввод.

## Remote-контракт

Каждый remote имеет одного владельца на сервере. Документируй:

- кто вызывает;
- тип и максимальный размер каждого аргумента;
- rate limit;
- серверные проверки;
- результат и ошибки;
- что происходит при повторе и выходе игрока.

Клиентский UI не считается доказательством контракта. Сервер должен отвергать неизвестные поля, неверные типы, NaN, слишком длинные строки и невозможные значения.

## Definition of Done

Система не готова, пока не выполнены acceptance criteria, Script Analysis чист, Output не получил новых ошибок, позитивный и негативный сценарии пройдены, а ограничения честно записаны.
