# Физика, коллизии, raycast, network ownership

## Физика: меньше, чем кажется

Главная мысль: **физика дорогая и недетерминированная**. Если объект должен двигаться предсказуемо, двигай его анимацией (`TweenService`, `CFrame`), а не силами. Физику оставь тому, что должно вести себя как физика: падающие ящики, машины, мячи.

- Всё статичное — `Anchored = true`. Неотъякоренная декорация не только падает, но и тратит бюджет физики каждый кадр.
- Современные констрейнты вместо устаревших Body-объектов: `AlignPosition`, `AlignOrientation`, `LinearVelocity`, `AngularVelocity`, `VectorForce`.
- `Massless = true` на деталях, приваренных к основной части: иначе оружие из десяти частей утяжеляет персонажа и он начинает странно прыгать.
- Не создавай сотни неотъякоренных частей за раз. Взрыв из 200 обломков положит сервер, а на телефоне даст фриз. 10-20 обломков плюс `ParticleEmitter` выглядят лучше и стоят копейки.
- `PhysicsService` и `Workspace.Gravity` меняй осознанно и в одном месте: разбросанные по коду изменения гравитации отлаживать невозможно.

## Collision Groups

Collision groups решают задачу "эти объекты не должны сталкиваться с теми". Без них разработчики начинают костылить через `CanCollide` в цикле, что даёт мигающие коллизии и баги.

Типичные группы в детской игре: `Players` (игроки не толкают друг друга), `NPCs`, `Projectiles` (пули не сталкиваются между собой), `Decor` (кусты не мешают ходить), `Debris`.

```lua
local PhysicsService = game:GetService("PhysicsService")

-- Регистрация делается один раз на сервере при старте.
PhysicsService:RegisterCollisionGroup("Players")
PhysicsService:RegisterCollisionGroup("Projectiles")

-- Игроки не толкают друг друга: критично в детских играх,
-- иначе толпа у магазина выпихивает друг друга с карты.
PhysicsService:CollisionGroupSetCollidable("Players", "Players", false)
PhysicsService:CollisionGroupSetCollidable("Projectiles", "Projectiles", false)

-- Назначение группы
for _, part in character:GetDescendants() do
	if part:IsA("BasePart") then
		part.CollisionGroup = "Players"
	end
end
```

Группу персонажу назначай в `CharacterAdded`: при респавне персонаж новый, и настройки сбрасываются. Забытое переназначение даёт баг "после смерти игроки снова толкаются".

## Raycast: правильный способ проверять попадания

`workspace:Raycast` заменил устаревшие `FindPartOnRay`. Всегда передавай `RaycastParams` с фильтром, иначе луч упрётся в самого стреляющего или в невидимые зоны.

```lua
local params = RaycastParams.new()
params.FilterType = Enum.RaycastFilterType.Exclude
params.FilterDescendantsInstances = { character }  -- себя не проверяем
params.IgnoreWater = true
params.RespectCanCollide = true  -- декор с CanCollide=false не мешает

local origin = muzzle.WorldPosition
local direction = character.PrimaryPart.CFrame.LookVector * MAX_RANGE
local result = workspace:Raycast(origin, direction, params)

if result then
	local hitPart = result.Instance
	local hitPoint = result.Position
	local normal = result.Normal   -- для разворота эффекта по поверхности
	local humanoid = hitPart.Parent and hitPart.Parent:FindFirstChildOfClass("Humanoid")
	if humanoid then
		CombatService.applyDamage(humanoid, DAMAGE)
	end
end
```

Важные детали:

- **Второй аргумент — это вектор направления с длиной, а не точка.** `direction.Unit * range`, не позиция цели. Передача точки вместо направления даёт луч, стреляющий из центра карты, и это классическая ошибка.
- `Exclude` фильтр удобнее `Include` в большинстве случаев: перечислить исключения проще, чем всё, во что можно попасть.
- Аксессуары и волосы персонажа могут ловить луч. Либо исключай их, либо проверяй, что попал в `BasePart` с родителем-персонажем.
- Для проверки "вижу ли я игрока" (NPC, стелс) raycast от глаз к цели с исключением обоих — самый дешёвый способ.
- `Blockcast` и `Spherecast` нужны, когда точка слишком точна: удар мечом лучше проверять объёмом, иначе игрок промахивается там, где визуально попал. В детской игре щедрая хитбокс-зона важнее честности.

Никогда не доверяй результату raycast, посчитанного на клиенте, для нанесения урона. Клиент присылает "я попал в X", сервер проверяет расстояние и правдоподобность сам, см. `security.md`.

## Network ownership

Roblox передаёт физику неотъякоренных объектов рядом с игроком его клиенту — так движение выглядит плавно без лага. Побочный эффект: клиент может врать о положении этих объектов.

```lua
-- Важный для геймплея объект: физика считается сервером,
-- клиент не может его телепортировать.
part:SetNetworkOwner(nil)

-- Транспорт игрока: наоборот, отдаём владение ему для отзывчивости.
vehicleSeat:SetNetworkOwner(player)
```

Правило: объекты, влияющие на результат игры (мячи, ключи, охраняемые предметы), держи на сервере через `SetNetworkOwner(nil)`. Транспорт и персонажа отдавай клиенту, иначе управление будет ощущаться вязким.

`SetNetworkOwner` работает только на неотъякоренных частях и только с сервера. На `Anchored` бросит ошибку — частая причина падения скрипта транспорта.

## StreamingEnabled

Включается на `Workspace` и заставляет клиента грузить только окружающую часть карты. Для больших миров это спасение по памяти на телефоне, но меняет правила игры для клиентского кода.

Что становится обязательным:

- Клиент **не может считать**, что дальний объект существует. `FindFirstChild` вернёт `nil` совершенно законно. Используй `WaitForChild` с таймаутом или подписку на появление через `CollectionService`.
- Важные для клиента объекты помечай `ModelStreamingMode = Persistent`, чтобы они не выгружались.
- Клиентские скрипты, обходящие `Workspace` целиком, начинают видеть неполную картину. Логику, зависящую от полного списка объектов, держи на сервере.
- Персонаж игрока и его окружение всегда загружены, поэтому локальная механика не страдает.

Если включаешь StreamingEnabled в существующем проекте — предупреди пользователя, что клиентский код надо перепроверить. Это изменение ломает молча, а не с ошибкой.
